# Glossary — Clean Architecture + Clean Code

> `A` = Clean Architecture chương N (arch-chNN), `C` = Clean Code chương N (code-chNN).

**Abstract component**: component chỉ chứa interface, rất ổn định (A14)
**Abstract Factory**: tạo object concrete mà không phụ thuộc source vào nó (A11, C3, C11)
**Accidental (false) duplication**: code giống nhau nhưng đổi vì lý do khác nhau; đừng gộp (A7, A16)
**Active Record**: DTO có `save`/`find`; không nhét business rule (C6)
**Actor**: nhóm người cần cùng một loại thay đổi; đơn vị của SRP (A7)
**ADP (Acyclic Dependencies Principle)**: không có vòng trong đồ thị component (A14)
**Argument object**: gom nhiều tham số thành một class (C3)
**Boundary**: đường ngăn hiểu biết giữa hai phía; vẽ theo trục thay đổi (A17, A18)
**Boy Scout Rule**: để code sạch hơn lúc bạn nhận nó (C1)
**BUILD-OPERATE-CHECK**: cấu trúc 3 phần của test sạch (C9)
**CCP (Common Closure Principle)**: gom thứ đổi cùng lúc, cùng lý do; SRP cho component (A13)
**Clean Architecture**: các vòng đồng tâm + Dependency Rule (A22)
**Code-sense**: cảm quan thấy lựa chọn để biến code bẩn thành sạch (C1)
**Cohesion**: mức độ method dùng chung biến của class (C10)
**Command Query Separation**: hàm hoặc làm, hoặc trả lời (C3)
**Component**: đơn vị deploy nhỏ nhất (jar/DLL/AAR/Gradle module) (A12)
**Critical Business Rules/Data**: quy tắc/dữ liệu kiếm tiền kể cả không có máy tính (A20)
**Cross-cutting concern**: mối quan tâm cắt ngang domain (log, transaction, security) (A27, C11)
**CRP (Common Reuse Principle)**: đừng bắt người dùng phụ thuộc thứ họ không cần (A13)
**D (Distance)**: `|A + I − 1|`, khoảng cách tới Main Sequence (A14)
**Data/Object anti-symmetry**: OO dễ thêm type, procedural dễ thêm hàm (C6)
**Data Mapper**: tên đúng của "ORM"; thuộc tầng DB (A23)
**Database Gateway**: interface truy cập DB do use case định nghĩa (A23)
**Decoupling mode**: source / deployment / service level (A16)
**Dependency Injection**: object thụ động nhận dependency; container/main lắp ráp (C11)
**Dependency Inversion (DIP)**: phụ thuộc abstraction, không phụ thuộc concrete volatile (A5, A11)
**Dependency Rule**: source dependency chỉ chĩa vào trong (A22)
**Device independence**: chương trình không biết thiết bị IO cụ thể (A15)
**DTO**: class public field, không hành vi (C6)
**Emergent design**: thiết kế nổi lên từ 4 quy tắc Simple Design (C12)
**Entity**: object chứa Critical Business Rules + Data (A20, A22)
**Event sourcing**: lưu transaction, không lưu state (A6)
**F.I.R.S.T.**: Fast, Independent, Repeatable, Self-Validating, Timely (C9)
**Fan-in / Fan-out**: phụ thuộc đi vào / đi ra một component (A14)
**Feature Envy**: method quan tâm data của class khác hơn class mình [G14] (C6, C17)
**Firmware**: code bị trói vào phần cứng/nền tảng (A29)
**Flag argument**: tham số boolean chọn hành vi; nên tách hàm (C3)
**Fragile Tests Problem**: test gắn chặt hệ thống, đổi nhỏ là vỡ nhiều (A28)
**HAL / PAL / OSAL**: lớp trừu tượng phần cứng / bộ xử lý / OS (A29)
**Humble Object**: phần khó test, giữ tối giản (A23)
**Hybrid**: nửa object nửa data structure, tệ nhất cả hai (C6)
**I (Instability)**: `Fan-out / (Fan-in + Fan-out)` (A14)
**Interactor**: hiện thực use case (A22)
**ISP (Interface Segregation Principle)**: đừng phụ thuộc thứ không dùng (A10)
**Law of Demeter**: chỉ nói chuyện với "bạn", tránh train wreck (C6)
**Learning test**: test khám phá API bên thứ ba (C8)
**Level**: khoảng cách tới input/output (A19)
**LSP (Liskov Substitution Principle)**: implementation phải thay thế được nhau (A9)
**Main component**: component bẩn nhất, tạo và nối mọi thứ (A26)
**Main Sequence**: đường nối (0,1) và (1,0) trên đồ thị A/I (A14)
**OCP (Open-Closed Principle)**: mở để mở rộng, đóng để sửa (A8, C10)
**Output port / Output boundary**: interface use case dùng để gửi kết quả ra presenter (A22)
**Partial boundary**: ranh giới giữ chỗ (skip last step / Strategy / Facade) (A24)
**Plugin architecture**: chi tiết cắm vào policy (A5, A17)
**Policy vs Details**: business rules vs IO/DB/framework (A15)
**POJO**: object thuần không phụ thuộc framework (C11)
**Presenter / View Model**: presenter format data thành String/boolean/enum cho View (A23)
**REP (Reuse/Release Equivalence)**: đơn vị reuse = đơn vị release (A13)
**Request/Response model**: data structure thuần vào/ra use case (A20)
**SAP (Stable Abstractions Principle)**: ổn định bao nhiêu thì trừu tượng bấy nhiêu (A14)
**Screaming Architecture**: cấu trúc hét use case, không hét framework (A21)
**SDP (Stable Dependencies Principle)**: phụ thuộc theo hướng ổn định (A14)
**Selector argument**: tham số chọn hành vi (boolean/enum) [G15] (C17)
**Simple Design (Beck)**: chạy hết test → không trùng lặp → biểu đạt → ít class/method (C1, C12)
**Special Case Pattern**: object xử lý trường hợp đặc biệt thay null/exception (C7)
**SRP (Single Responsibility Principle)**: một module, một actor (A7); một lý do để thay đổi (C10)
**Stepdown Rule**: đọc từ trên xuống, mỗi hàm theo sau là mức thấp hơn (C3)
**Successive refinement**: viết nháp rồi tinh chỉnh qua nhiều bước nhỏ (C14)
**Temporal coupling**: thứ tự gọi bắt buộc bị ẩn [G31] (C3, C17)
**Test API (testing API)**: API riêng cho test, có "superpowers" (A28)
**Three Laws of TDD**: chỉ viết production khi có test fail… (C9)
**Train wreck**: chuỗi `a.b().c().d()` (C6)
**Zone of Pain / Zone of Uselessness**: ổn định+cụ thể / trừu tượng+không ai dùng (A14)
